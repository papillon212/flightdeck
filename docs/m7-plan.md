# M7 편집 기록 서버 — 구현 계획

- 기준: [design.md](design.md) v0.17 §8.6(편집 기록), §3.5(위치 고정), §7.3 6(서버 coverage 재계산), §7.4(직접 수정 메모·외부 변경), §11.3 5, §14 M7
- 완료 기준: **모든 hunk의 출처가 조회되고, 쓰레드가 대규모 수정 후에도 위치 유지**
  - 리뷰어처럼 편집 기록을 갖지 않은 멤버도 서버에서 줄 단위 출처를 본다(에디터 hover).
  - 반영 서버가 서버의 편집 기록으로 coverage를 다시 계산하고, 설명 없는 변경이 있으면 반영하지 않는다.
  - 코드 쓰레드가 그 줄 자체가 고쳐지거나 위아래로 큰 수정이 있어도 편집 기록으로 따라간다(diff 줄 매핑이면 "위치 잃음"이 되는 경우).

## 이미 있는 것 (M1~M5)

- 로컬 편집 기록(`<git 공용 폴더>/flightdeck/editlog/<epic>.jsonl`): 에디터·에이전트·셸·수정 제안·렌더링·복원·외부 반영·외부 변경 출처, 쓰기 직렬화, IME 묶음.
- 문자 단위 출처 재적용(`provenance`), hunk 분류(`coverage`), Step별 변경(impl-log `changes` 자동, M4), 앵커 변환(`transformAnchor`, M1).
- 체크포인트 trailer `Flightdeck-Seq`.

## 미리 보이는 설계 문제 (구현 전 제안)

| # | 절 | 현재 서술 | 문제 | 제안 |
|---|---|---|---|---|
| E1 | §8.6 전송 | 생기는 즉시 WebSocket으로 보낸다 | 편집 기록의 원천은 로컬 파일이고, 실시간이 필요한 쪽은 관찰(M8)이다. 저장·조회만 보면 REST가 단순하고 재전송도 쉽다 | 저장은 **REST 묶음 업로드**(`POST /editlog {epic, from_seq, records, memos}`)로 한다. 서버는 seq가 이어지는지만 보고(빈칸이면 409 + 서버의 마지막 seq), 확장은 그 뒤부터 다시 보낸다. 확장은 5초 주기·제출 전·체크포인트 뒤에 올린다. 실시간 스트림(M8)은 같은 기록을 따로 중계한다 |
| E2 | §8.6 | 서버는 `base_hash`로 순서를 검증한다 | 서버가 받을 때마다 재적용하면 무겁고, 재적용에는 base 내용(git)이 필요하다 | 받을 때는 seq 연속·작성자만 본다. **재적용 검증은 쓸 때**(반영 coverage, 출처 조회) 한다. 불일치는 그 결과에 "기록 불일치"로 드러난다 |
| E3 | §8.6, §7.3 6 | 서버가 편집 기록으로 coverage를 다시 계산 | 담당자는 리뷰 요청 뒤에도 계속 편집할 수 있다. 서버는 검증한 커밋이 편집 기록의 **어디까지**에 해당하는지 알아야 한다 | 확장이 에픽 브랜치에 공유 커밋을 만들 때 trailer **`Flightdeck-Seq: <n>`**(그때까지의 편집 기록)를 넣는다. 서버는 seq ≤ n 기록만 base 위에 재적용해 그 커밋의 파일과 같은지 보고, 같으면 coverage를 계산한다. 다르면 "기록 불일치"로 반영하지 않는다. trailer가 없는 커밋(이전 에픽)은 지금처럼 확장의 계산을 믿는다 |
| E4 | §8.6 작성자 | — | 아무 멤버나 남의 에픽 편집 기록을 올리면 출처가 오염된다 | 올릴 수 있는 사람은 그 에픽의 담당자(M8부터 현재 조종수). 기록의 출처 멤버는 확인하지 않는다(외부·렌더링 출처가 있다) |
| E5 | §3.5 | 앵커는 `{file, seq, offset_start, offset_end}` | M5 코드 쓰레드 앵커는 `{file, rev, range(줄)}`다. 바꾸면 이전 쓰레드를 읽을 수 없다 | 앵커는 그대로 두고 **seq를 더한다**(`seq?` = rev 커밋의 `Flightdeck-Seq`). 위치 계산: rev의 그 줄 범위를 문자 오프셋으로 바꾸고, seq 뒤의 편집 기록으로 옮긴 뒤 다시 줄로. 범위 전체가 지워졌을 때만 "위치 잃음". 편집 기록이 없거나 rev에 seq가 없으면 diff 줄 매핑(M5) |
| E6 | §8.6 에디터 통합 | 줄에 마우스를 올리면 출처 | 리뷰어는 담당자의 편집 기록이 없다 | 담당자 창은 로컬 편집 기록으로, 다른 창은 서버 `GET /editlog/<epic>/blame?file&rev`로 계산한다. 서버는 rev 커밋의 seq까지 재적용한다. 결과는 줄마다 `{kind, member, run?, step?, memo?}` |
| E7 | §7.4 외부 변경 | M1은 산출물만, 코드 전체는 M7 | M4는 체크포인트·제출 때만 잡는다 | 담당자 창에서 작업 폴더 파일 감시(1초 디바운스)로 저장되지 않은 에디터 파일이 없는 파일만 재적용 비교 → 차이를 `external:unknown`으로 기록하고 "Flightdeck 밖에서 수정됨: 파일" 알림. 에이전트 실행 중(훅의 도구 구간)에는 미룬다 |
| E8 | §7.4 메모 | 로컬 저장 후 M7에서 서버로 | — | 메모도 같은 업로드 묶음으로 올린다. 반영 서버의 coverage 재계산이 메모를 쓴다 |

찾아 고친 것:
- 확장이 "서버의 마지막 seq만" 물을 때 쓴 큰 수가 PG `integer` 범위를 넘어 업로드가 계속 실패했다(메모리 저장소 테스트로는 안 드러남). 서버에서 범위 안으로 자르고, PG 저장소 테스트(`FD_TEST_PG`, 별도 시험 DB `flightdeck_test`)에 편집 기록 검사를 넣었다.
- 1차 실행의 외부 변경은 제출 검사가 먼저 잡아 파일 감시를 확인하지 못했다. 시나리오를 고쳐 2차에서 확인했다.
- 시나리오 환경: M5.5 때 띄운 VS Code 인스턴스가 종료되지 않고 남아 있어(종료 명령이 본 프로세스를 잡지 못함) 첫 실행이 그 인스턴스에 창만 더했다. 끝난 M5.5 에픽을 다시 읽기만 했고 이벤트는 남기지 않았다. 종료 방법을 고치고 시험용 VS Code 설정에 창 복원 끄기를 넣었다.

확인하지 못한 것: 사람이 마우스로 올리는 hover 표시(같은 hover 제공자를 VS Code 명령으로 불렀다), retention 정리.
