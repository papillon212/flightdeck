# M3 설계 티어 — 구현 계획

- 기준: [design.md](design.md) v0.12 §14 M3, §4.1·§4.2, §5 `phases.design`, §3.4
- 완료 기준: **설계가 2티어 통과**
  - 담당자가 설계 초안을 리뷰 요청한다.
  - 1티어(lead) 리뷰어가 승인한다.
  - 2티어(architect) 리뷰어가 수정 요청 쓰레드를 단다. 담당자가 고쳐 다시 요청하면 `reapproval: on_change`에 따라 1티어부터 다시 승인받는다.
  - 2티어가 승인하면 IMPLEMENTATION으로 넘어간다.
  - 승인은 모두 서버 서명이고, 서명 없는 승인·차례가 아닌 승인·바뀐 문서에 대한 승인은 무시된다.

## 범위

| 포함 | 제외 (이후 마일스톤) |
|---|---|
| DESIGN 하위 상태: `owner_review` → `tier[1..n]_review` (§4.1) | 리뷰 전용 사본(`#review-<member>`)과 수정 제안 패치·`patch.applied` (M5, 코드 리뷰와 함께) |
| 리뷰 요청·티어 승인 서버 서명, 리뷰어 자격·차례·`artifact_hash` 검증 (§4.2, §12) | 리뷰어 직접 수정 `review.edited` (W5) |
| `reapproval: on_change` 재승인 | IMPLEMENTATION 단계의 실제 작업 (M4) |
| 리뷰어의 수정 요청·질문 쓰레드 (§3.4 "현재 티어 리뷰어") | (W4 결정으로 `skip` 규칙 자체를 없앰. 리뷰어 없는 티어 건너뛰기는 포함) |
| 리뷰 차례 알림: VS Code + 일감 멘션 (§3.7, §4.2) | |
| 리뷰어 창: 리뷰 요청 커밋의 읽기 전용 창에서 쓰레드 생성·승인 | |

## 미리 보이는 설계 문제 (구현 전 제안)

| # | 절 | 현재 서술 | 문제 | 제안 |
|---|---|---|---|---|
| W1 | §4.1 DESIGN, §3.1 | DESIGN 하위 상태 `agent_drafting → owner_review → tier[1..n]_review`. 종료 조건 "각 티어 승인 + 열린 쓰레드 0" | 담당자 검토가 끝나 **티어 리뷰가 시작되는 시점을 나타내는 이벤트가 없다**. `phase.completed`는 "단계를 넘김"이라 DESIGN에는 맞지 않는다. 리뷰어가 무엇을 승인하는지(어느 내용)도 정해지지 않는다 | 서버 서명 이벤트 `review.requested {phase, artifact_hash, commit}`를 추가한다. 담당자가 산출물을 공유하고 요청하면 서버가 원격 문서의 형식·해시를 확인해 서명한다. 리뷰어는 이 커밋을 본다. DESIGN의 단계 넘김은 별도 `phase.completed` 없이 **마지막 티어 승인으로 자동**이다 |
| W2 | §4.2 | `reapproval: on_change`이면 `artifact_hash`가 현재 산출물과 같아야 한다. 다르면 그 티어부터 다시 승인 | reducer는 파일을 보지 못해 "현재 산출물"을 모른다. "그 티어"가 어느 티어인지도 모호하다 | "현재 산출물" = **마지막 `review.requested`의 해시**. 담당자가 고치면 다시 요청해야 한다. 그 해시와 다른 승인은 모두 무효이고, 현재 티어 = 유효 승인이 모자란 첫 티어. 결과적으로 **1티어부터 다시**가 된다. `never`면 이전 승인을 유지한다. 서버는 승인 요청 시 해시가 마지막 요청 해시와 원격 문서 둘 다와 같은지 본다(요청 뒤 몰래 고친 문서 승인 방지) |
| W3 | §4.2, §3.4 | 리뷰어가 해당 티어 멤버여야 한다 | 담당자가 그 그룹에 속하면 **자기 설계를 승인**할 수 있다. 같은 사람이 두 티어를 모두 승인할 수도 있다 | 담당자 자신의 승인은 무효. 한 사람의 승인은 한 티어에만 센다(앞 티어에서 이미 승인한 사람은 뒤 티어에서 세지 않음) |
| W4 | §5 `design.skip` | `tracker_tags`, `size` 조건으로 티어를 건너뛴다 | 판단 재료(일감 태그·크기)는 담당자의 일감 도구 토큰으로만 읽힌다. 서버는 일감 토큰이 없어 확인할 수 없고(§11.3), 담당자가 적어 보내는 값을 믿어야 한다. 크기(size)를 어디서 읽는지도 정해지지 않았다 | M3에서는 `skip`을 구현하지 않고 미결로 둔다. 이후 방안: (a) 서버가 읽기 전용 일감 도구 토큰을 갖고 직접 확인 (b) 어드민이 에픽별로 건너뛰기를 승인. 결정 전까지 skip 규칙이 있는 설정도 모든 티어를 거친다 |
| W5 | §4.2 리뷰어 직접 수정 | 확장이 에픽 브랜치에 커밋하고 `review.edited`를 남긴다 | 에픽 브랜치에 쓰는 사람은 조종수 한 명이다(D17). 리뷰어가 직접 커밋하면 담당자 작업 폴더와 충돌하고, 편집 기록(§8.6)의 단일 순서열이 깨진다 | 리뷰어 직접 수정을 없애고 **수정 제안(패치) → 담당자가 반영**(§9.3, `patch.applied`)으로 통일한다. 패치는 M5에서 코드 리뷰와 함께 만들고, M3의 수정은 쓰레드로 요청한다 |
| W7 | §3.6, §9.3, §2.4 | 개인 질문은 읽기 전용 사본에서 열고 훅이 쓰기·셸을 막는다. 리뷰어의 에이전트는 결과물·handoff·diff·`search_run`을 맥락으로 받는다 | M2의 읽기 전용 창은 **VS Code에서만** 읽기 전용이다. 거기서 연 에이전트는 파일 편집·셸이 막히지 않고, Flightdeck MCP 도구(에픽·쓰레드·handoff)도 없다. 리뷰어가 에이전트로 문서를 검사하다 고친 내용을 보고 판단할 수 있다(그 변경은 다음 공유 커밋 때 버려진다) | 읽기 전용 창에도 에이전트 설정을 넣는다: 훅은 **리뷰 정책**(산출물 파일 `analysis.md`·`design.md`만 쓰기 허용 — W8의 쓰레드 초안용, 그 밖의 파일 쓰기 거부, 셸은 읽기 전용 명령만), MCP 도구는 그대로(`flightdeck_get_epic`·`list_threads`·`get_handoffs`). 실행 기록(`run.*`)과 편집 기록은 남기지 않는다(§3.6 기록 안 남김). 명령 "내 에이전트에게 묻기": 선택한 쓰레드·문단을 인용해 그 창에서 Claude Code를 연다. `search_run`은 세션 원본 저장과 함께 M4 |
| W8 | §3.2, §3.1, §3.6 | 쓰레드 블록은 확장이 그리는 영역이라 직접 고쳐도 다시 그리면 사라진다. 쓰레드는 Comments 화면에서 만든다 | 리뷰어(와 담당자)가 **자기 에이전트에게 질문·답글·코멘트를 달라고 지시할 방법이 없다**. 에이전트가 가장 잘하는 것은 파일 편집인데, 문서에 쓴 내용은 렌더링에 지워진다. `thread.created`에는 에이전트가 썼다는 표시(`source`)도 없다 | **쓰레드 초안 블록**을 둔다. 에이전트(또는 사람)가 문서의 대상 블록 바로 아래에 쓴다:<br>`<!-- flightdeck:draft kind=question to=dh.lee -->` 본문 `<!-- /flightdeck:draft -->` (새 쓰레드, 앵커 = 바로 위 블록의 문단 ID)<br>`<!-- flightdeck:draft reply=t-XXXXXXXX -->` 본문 `<!-- /flightdeck:draft -->` (답글)<br>확장이 저장·파일 변경 때 초안을 찾아 Comments에 **초안으로 표시**하고, 사람이 "올리기"(한 건씩 또는 모두)를 누르면 이벤트로 쓴다. 메타 브랜치는 append-only이고 작성자 이름으로 남기 때문이다. 이벤트에 `source: agent`를 남긴다(`thread.created`에도 `source` 추가). 읽기 전용 창에서는 **초안 블록 밖의 변경을 되돌린다**(리뷰어는 문서 내용을 고치지 않는다, W5). 담당자 창에서도 같은 문법으로 에이전트가 답글 초안을 쓸 수 있다 |
| W6 | §3.4, §4.2 | 쓰레드 생성: 해당 단계 담당자 / 현재 티어 리뷰어. 종료: 각 티어 승인 + 열린 쓰레드 0 | 리뷰어가 연 쓰레드가 열린 채로 그 티어를 승인할 수 있는지 정해지지 않았다 | 승인하는 리뷰어 **본인이 연 열린 쓰레드가 있으면 그 승인은 거부**한다(먼저 해결). 다른 사람의 열린 쓰레드는 막지 않되, 마지막 티어 승인 시점에는 열린 쓰레드가 0이어야 단계가 넘어간다 |
